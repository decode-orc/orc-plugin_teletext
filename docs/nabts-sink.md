# NABTS Sink

| | |
|-|-|
| **Stage id** | `nabts_sink` |
| **Stage name** | NABTS Sink |
| **Connections** | 1 input → no outputs |
| **Purpose** | Recover North American Basic Teletext from the VBI of a 525-line source, export the packet stream, and browse the records the recording carried |

**Use this stage when:**

* Preserving the NABTS data carried by an NTSC or PAL-M capture — CBS ExtraVision, NBC Teletext and their contemporaries
* Reading the pages a recording carried without leaving decode-orc
* Producing a `.t33` packet stream, or per-record files, for an external NAPLPS tool

**What it does**

NABTS is **ITU-R BT.653 System C**, specified by CEA-516 (formerly EIA-516): 5.727272 Mbit/s in 33-byte packets on the 525-line signal. Its presentation layer is **NAPLPS** (ANSI X3.110-1983, also ITU-T T.101 Data Syntax III), so a page is a drawing program rather than a grid of characters — lines, arcs, polygons, mosaics and redefinable characters as well as text.

Triggering the stage makes one linear pass over the whole frame range and carries the recovery up through every layer CEA-516 defines. It probes the candidate VBI lines of both fields of every frame, recovers the packets and writes them as a flat, headerless stream in strictly temporal order (frame → field → ascending line), keeping their transmission coding — Hamming 8/4 on the five prefix bytes, odd parity on the data block — so a consumer decodes the stream exactly as a receiver decodes a live broadcast. Above that it reassembles the packets into data groups per data channel, decodes the teletext record in each group and joins any linked series back into one message, and interprets the NAPLPS of a presentation record into a display list. An application record's data is decoded as function descriptors instead.

Pages are presented the way a receiver would present them. A record whose support-needed flag is set (§5.2.7.9) is drawn after its data channel's support record (address FFF), so the macros, redefinable characters and colour maps a service shares across its pages reach them; a caption record is drawn from the caption preset of §5.2.7.3. A record that names a More Record (§5.2.7.6, or explicitly in a header extension, §5.2.8.4) is a chain: each member is drawn over the display the members before it left, and the viewer lists the chain as one page whose members are stepped through as sub-pages.

A data group of a type other than zero is not teletext and is not decoded, but it is not silently dropped either: a channel whose groups arrived with their channel and header received as transmitted is named in the viewer's notices and in the report's **Not teletext** lines, with its group type and group count. A recording carrying nothing else (for example a 1992 CBS recording whose single channel is type-15 private data) triggers to an empty list that says so.

Frames are decoded on several threads while the stream is written from one, and the pass learns where in the line this recording puts its data and which lines carry it, so later frames cost far less than the first ones. The thread count changes nothing in what is recovered (see `decode_threads` below). The learning is always on, and it is built not to lose data: a search narrowed to where this recording's data bursts start that finds nothing is repeated over the full window, and the full line window is read again periodically, so a service that starts part way into a recording is still picked up.

The catalogue of records rides along with the packet stream, which is why this is a sink rather than an analysis sink. That is what the **NABTS Records** tool shows, and leaving `output_path` empty makes it the only thing the run produces.

!!! warning "Not World System Teletext"

    On a 525-line capture NABTS and WST share the clock run-in, the bit rate, the VBI lines and the data levels, and are told apart by the framing code alone — `0xE7` against `0xE4`. Use the **Teletext Sink** for WST. A stage pointed at the wrong service recovers nothing rather than recovering nonsense, so a run that finds almost no packets is the signal to try the other one.

Recovery quality tracks the source's luma bandwidth, and NABTS is far less forgiving of a marginal tape than WST is: a WST page is a grid of independent parity-coded bytes, so damage stays where it lands, while a NABTS record is a stateful byte stream in which one wrong byte changes how the several after it are read. The report's **mean decision confidence** is the number to read first — around 0.5 and above, expect readable pages; approaching 0.2, the recording is at the noise floor and no amount of decoding will recover a page from it. The two reference recordings bracket the range: a VHS SP capture of ExtraVision reads at 0.55 with 0.02 % of record bytes failing parity, while a VHS EP capture of NBC Teletext reads at 0.22 with 7.10 % failing, and browses as nonsense.

**Parameters**

* `output_path` (file path)
    - Path to the output packet stream; the `.t33` extension is appended if absent.
    - Optional. Left empty, the run decodes exactly as it would but writes no file, which is what to do when the records themselves are what you are after — the **NABTS Records** tool is filled either way. `write_report`, `export_data`, `export_records` and `export_captions` are all written beside the packet stream, so enabling any of them without a path fails the run.
* `first_vbi_line` (integer)
    - First candidate field line probed, 1-based, both fields. Range: 1–22.
    - Default: `10`.
* `last_vbi_line` (integer)
    - Last candidate field line probed, 1-based, both fields. Range: 1–22. With the above this gives the window of CEA-516 §1.1.1 and ITU-R BT.653 §2: broadcast lines 10–21 and 273–284. The full-field transmission CEA-516 §1.2 also permits (lines 10–262) is not covered.
    - Narrowing the window to the lines a service actually uses is worth doing: unused lines still yield the occasional packet whose prefix decodes by chance, which opens groups that never complete and consumes continuity indices belonging to real ones. Read the report's per-line table — a line carrying a service shows a large, steady packet count, one fitted to noise a high burst count and a small packet count. On an NBC EP transfer, going from 10–21 to 15–16 cut refused group headers from 19,691 to 1,675 and recovered seven more records.
    - Default: `21`.
* `keep_empty_packets` (boolean)
    - Emit a whole zero packet for candidate lines with no data so packet position maps 1:1 to (frame, field, line).
    - Default: `false`.
* `detector` (string)
    - How data bits are recovered: `Threshold` (slice at bit centres; exact on direct captures), `MLSE` (fit the recording's frequency response to the known start of each line and detect against it; recovers data from tape, where limited bandwidth smears bits into their neighbours), or `Automatic` (threshold first, MLSE only where it fails, so a clean source pays nothing extra).
    - Default: `Automatic`.
* `calibrate_bit_clock` (boolean)
    - Learn the bit clock the recording was sampled at, and read it at that clock. A capture card sampling against its own crystal rather than the video reads the data a little faster or slower than the standard's bit rate — a few hundredths of a per cent is up to a third of a bit by the end of a packet — which costs the last bytes of packets that were marginal already. The first packets are read again at a range of trial clocks, and once 400 have been scored the clock at which the most packets arrive with every byte checking out is adopted for the rest of the recording, provided it beats the standard's clock by more than chance allows (the scoring goes on to 800 and 1,600 packets where the lead is growing but not yet clear). A time-base-corrected capture scores within noise at every trial and keeps the standard's clock. The report says which clock the recording was read at, and on how many packets.
    - Default: `true`.
* `grammar_assisted_vote` (boolean)
    - A record no undamaged copy of ever arrived is recovered by voting its copies together byte by byte (see Notes), and some positions the copies leave exactly level — two of them disagreeing once each, which the vote can only settle by taking the most recent. Ask the NAPLPS grammar about those positions instead: the record is read through the linter with each candidate in place, and the one that leaves it best formed wins, or none of them where the grammar has no preference. It is asked only about level positions, never about one the evidence settled, and only about presentation records — an application record's data is not NAPLPS. Unlike **Syntax repair** in the record viewer, this changes the recovered record data itself, and so the files `export_records` writes and every later reading of the record, which is why it is a parameter rather than a viewer control. The packet stream is untouched either way. The report says how many positions were level and how many the grammar settled.
    - Default: `true`.
* `decode_threads` (integer)
    - Threads to recover lines on; `0`, the default, uses one per processor. Range: 0–256. The recovered stream is identical whatever this is set to, so lower it only to leave the machine free for other work.
    - Default: `0`.
* `write_report` (boolean)
    - Write the run's diagnostic report next to the packet stream under its full name plus `.txt` (`mydata.t33` gives `mydata.t33.txt`), so it needs `output_path` set. Beyond the packet-level recovery profile it accounts for every layer above: packets orphaned rather than placed in a group, groups completed, record headers refused, linked series joined, records catalogued. The same report always goes to the log at debug level.
    - Default: `false`.
* `export_data` (boolean)
    - Write everything the run decoded into a folder beside the packet stream, named after it plus `.export` (`mydata.t33.export`): the records as sent, the captions as subtitles, the datacasts and the files they carried, the network services' items, the report and a README. The same files the **NABTS Records** viewer's **Export All…** writes under `data/`, and the way to get them from `orc-cli`.
    - Default: `false`.
* `export_records` (boolean)
    - Write each record as its own file beside the packet stream, named for the channel, record address and version that identify it (`mydata.t33.000-1A4-v2.rec`). The file holds the record's data as the record viewer reads it — NAPLPS presentation code, or application data for a type 2 record — which is what to hand to an external NAPLPS tool. Where an undamaged copy arrived that is that copy byte for byte; where none did, it is the combination of the damaged copies (see Notes). Byte parity is left in place.
    - Default: `false`.
* `export_captions` (boolean)
    - Write the recording's captioning as a SubRip file beside the packet stream (`mydata.t33.srt`). The cues are the records the service marked with the caption flag of CEA-516 §5.2.7.3 — the flag, not the data channel, is what selects them — in transmission order, each running until the next replaces it (a caption record with no text is an erase and ends the cue before it), timed from the 59.94 fields per second of SMPTE 170M. Colour and positioning are dropped; SRT carries the plain text. The cues are always taken from the syntax-repaired reading of the records. A recording that carried no captioning writes no file.
    - Default: `false`.
* `reference_records` (string)
    - Other recordings of the same service, separated by semicolons: the packet streams (`.t33`) this stage wrote for them, the record files `export_records` wrote beside those streams, or folders of either — `C:\teletext\day1.t33; C:\teletext\day2\`. They are read at the end of the run, and the record viewer's **Reconstruct lost data** fills a lost stretch from their records as well as from this recording's own. Nothing else uses them: they change neither the recovery nor anything a run exports. A folder's record files are read in place of its streams, which take far longer to read (a stream is replayed through the same reassembly and vote as the recording's own packets). This run's own stream and records are skipped if listed, and a path that cannot be read is reported and passed over. The report's **References** line says how many records were read from how many streams.
    - The best references are recordings of the same service, close in time, whose received bytes can be trusted: what a reference holds in a stretch is copied as it stands.
    - Default: empty (rebuild from this recording's own records alone).

**Stage tools**

* **NABTS Records** — the record viewer for this node. It lists every record the range carried, with its channel and record address, version, record type, how often it was seen and over which frames, the section of the service it belongs to, and the classification flags the service set. It opens automatically when the node is triggered, which is how the records are reached: leave `output_path` empty and triggering the node is a decode-and-browse with no file written. The catalogue stays with the stage afterwards, so closing the viewer and picking **NABTS Records** from the **Stage Tools** menu re-opens it immediately rather than decoding the source again; on a node that has not been triggered that entry says there is nothing to show instead of starting the decode itself. Editing any stage's parameters rebuilds the graph and discards the catalogue with it, closing the viewer — trigger again to rebuild it from the new settings. Because the catalogue comes from a pass over the whole source rather than a window around the preview position, the list is the service's full carousel.
    - **Finding pages.** **Page** finds a page by its number, as a decoder of the day took one (three digits are a short address, four reach a service's long addresses). **Back**, **INDEX**, **NEXT** and **MORE** move between pages as the decoder's keys did, following the Next, More and Index records the page's header names, and the page numbers the page on screen offers are listed beside them as links. The **Section** column says which section of the service a page belongs to, from the index records the pages name or the sections the Master Index lists. Pages played as games are marked **Game: keypad** or **Game: quiz**.
    - An address that carried more than one record outside a More chain — a carousel giving each page the next version, a page revised while the recording ran — is listed as one page whose records are stepped through as sub-pages in the order they first arrived, as a receiver left on the page showed them. A More chain is listed the same way, each member drawn over the display the members before it left.
    - A **presentation record** is drawn as its NAPLPS display list, beside the plain text of the page in reading order — an index page is mostly words, and picking them off a rasterised page is tedious. **Show display area** outlines the lower 0.78125 of the unit screen that every receiver is guaranteed to show (ANSI X3.110 Table D1), which is how to tell a record drawn deliberately into one corner from one that was mis-scaled. **Show text** puts the text pane away, giving the page the whole width.
    - An **application record** is shown as its function descriptors instead, each with its code in the code-table notation of §7.2.2 and its arguments. A record sent with nothing to draw is named for the role its header gives it (**Cyclic Marker**, **Support Record**, **Auto Acquire**, or **Empty record**), and a record carrying another service's data under a presentation type is listed as that data and marked **Not NAPLPS** rather than drawn as stray shapes.
    - **Receiver** chooses which of four resolutions the page is drawn against, and is the only control for it — there is no parameter, on purpose. ANSI X3.110 draws into an abstract unit screen but sizes stroke width, line-texture dot and dash lengths, hatch spacing and the incremental raster in the physical pixels of the receiver displaying them (§5.3.2.2.6), so a page has no single correct appearance until a receiver is named. `256 x 200 (reference receiver)` is the grid Table D1 item 10 requires, which is what a set-top decoder of the period put on screen and what the window opens on; `512 x 400` and `768 x 600` are that grid at twice and three times, for a sharper reading of the same page; `256 x 200 (vector)` draws the reference receiver's page as shapes rather than pixels, smooth at any zoom but without the staircase a receiver drew a slanted edge with. Only whole multiples of the reference grid are offered: a page is authored against it, and a fraction of it lands between pixels, thickening strokes unevenly and breaking letterforms. The built-in character patterns follow the receiver too — `256 x 200` draws text from a 6 by 10 face, `512 x 400` from a 10 by 20 and `768 x 600` from a 9 by 15 at double size, all from the public-domain X11 misc-fixed family — and a heading is drawn in a larger face, as the receivers of the day drew one. Picking a receiver redraws the page you are looking at without reading the recording again, and nothing is saved with the project.
    - **Enable animations** plays the record the way a receiver put it on screen, on the timing the record itself carries: a page that uses WAIT (§5.3.2.8) appears in its stages, a clear part way through blanks what came before, and each blink process alternates its colour map entry — everything drawn in that colour — with the second entry the record named, on the ON and OFF intervals the record gave it. **Receiver pace** draws every command at the speed the Norpak TTX 650 drew it, and **TU-2000x pace** at the Panasonic TU-2000x's, both measured from the receivers' firmware, so a busy page is seen being built up and fills and clears sweep across the screen. A record that changes as it is shown has playback controls under the drawing — play and pause, **Replay**, step back and forward, a slider to seek, **Speed** and **Loop**. Clear the box to hold the finished record still for reading or capture.
    - **Option keys** play a page that was made to be played: a page that links macros to the digit keys and never runs them itself is marked **Game: keypad**, and while it is on screen a keypad stands beside the drawing. Pressing a digit runs its macro from the state the page and every key before it left, as a decoder did; **Reset game** shows the page as sent again.
    - **Reconstruct lost data** rebuilds the bytes the recording never received, and puts right the bytes it received failing parity, where another record — another page of this recording, or the same page in one of the `reference_records` — has the same bytes all round the stretch. It is **off** until you turn it on. Pages drawn from rebuilt or corrected bytes are marked `~` beside their address, and the line above the message panel says what was done to the page on screen.
    - **Syntax repair** presents a damaged page as recovered rather than as transmitted. It is **off** until you turn it on: what the viewer shows to begin with is what the recording carried. NAPLPS has a published grammar (ANSI X3.110-1983), so a page recovered from a damaged recording can be checked against it. A byte is changed only where the recording proves it wrong — it failed the odd parity of CEA-516 §3.3 — and only where the grammar leaves exactly one thing it could have been; where it leaves more than one, nothing is changed and the count of what was left undecided is reported. It never alters a byte that arrived cleanly, never fills in a byte that never arrived (it instead cuts the drawing at the last whole operand before a hole and salvages the whole shapes beyond it), never touches a byte that changes how the bytes after it are read (an escape sequence, a locking shift, DOMAIN or RESET), and never makes a change that would redraw the page. Pages it altered are marked with `*` beside their address in the list, and the message panel says how many pages were altered and how many now draw differently. With **Reconstruct lost data** on as well, the repair reads each page as the reconstruction left it.
    - Neither **Reconstruct lost data** nor **Syntax repair** changes what a run exports: the packet stream, the record files and the report always carry the recording's own bytes (the caption file is the one exception, always written from the repaired reading). The run's report carries the repair totals under **NAPLPS lint**.
    - **Caption track** is the list's one item for the caption service: selecting it shows the recording's captioning as a list of cues with their timings. §7.3.10 carries captioning as a run of records that each replace the last, so the cues rather than the individual records are what the service says.
    - **Save PNG…** writes the record on screen out as an image at the 4:3 shape of its display area, drawn as the record stands once finished (every stage drawn and every colour at rest), with **Show display area** honoured and the text pane left out, named for the record's channel, address and version (`Record-000-1A4-v0.png`). Every receiver saves at the same 1536 by 1152, a whole multiple of every grid, so receivers can be compared image to image. **Save SVG…** writes a presentation record as an SVG drawing that plays as the viewer does — stages and blinks as SMIL animation a web browser runs with no script. **Save All PNGs…** and **Save All SVGs…** write every drawn record into a chosen folder in one pass, with a progress dialogue that can be cancelled partway; application records are listings and are skipped. **Export All…** writes everything the run found into a folder chosen once: under `views/` what the viewer shows, and under `data/` what the stage decoded — the same files `export_data` writes, taken from what the last trigger left, so nothing is decoded again.
    - The panel along the foot of the window is where everything the viewer has to say is collected: what record you are looking at and what shape it is in, what the catalogue as a whole carries, and how the run went.
    - The full description of the viewer, as orc-gui shows it when you right-click the stage and choose **Help...**, is in [`src/nabts_sink/instructions.md`](../src/nabts_sink/instructions.md).

**Notes**

* Projects that set `tolerant_framing`, `require_valid_prefix`, `pin_data_phase` or `learn_active_lines`, which this stage no longer takes, still load: the setting is ignored and the log says so once.
* NTSC and PAL-M sources are accepted. A 625-line source reports an error: CEA-516 §1.1.1 specifies NABTS on the 525-line signal, and no 625-line service exists to recover.
* This stage writes no CSV — its file output is the packet stream, and optionally the per-record files, the caption document and the report.
* Nothing is corrected in the packet stream. Where a packet carries the longitudinal check byte of §3.4, that byte and the per-byte parity form a product code and a single-bit error in the data block is located and corrected before the record layer sees it; whether a service sends it is the service's choice.
* Byte parity is not used to repair damaged bytes in the packet stream as it is for World System Teletext: CEA-516 §3.3 gives the data block odd parity only when its data group is of type 0, and a single packet does not say which type its group is. By the time a record is assembled the group type is known, so at the record layer a byte that fails parity is known to be corrupt.
* **Repeated copies are combined.** Where no copy of a record ever arrives undamaged, the damaged copies the carousel brought round are voted together byte by byte: a parity-clean value beats a corrupt one however often the corrupt one arrived, and among equals each copy is weighted by how sure the detector was of its byte, with a tie going to the most recent copy (or to `grammar_assisted_vote`). The moment an undamaged copy arrives it is used as it stands. The most recent sixteen copies are kept for the vote; the record viewer says how many a record was combined from.
* Only copies that line up position for position vote: a copy whose group lost packets, or an incomplete linked series, counts as an appearance but is kept out of the vote. A copy that agrees with less than half of a first vote is dropped from a second, which keeps out packets of other records mis-addressed into this one, and a copy whose data starts in the wrong place (a misread header announcer) is tried slid up to eight bytes either way before being ruled out. A position no copy ever received is left as NUL, a transparent control with no presentation effect, rather than letting the record close up over the hole.
* **Phantom records are pruned.** A three-bit burst can resolve a Hamming 8/4 identity digit silently into a neighbouring codeword (MLSE damage commonly carries digit 0 onto 7), filing a record under an address the service never sent. A record no copy ever named as transmitted is folded into the one attested identity a single hexadecimal digit away, or removed if there are several such or none. The report and the viewer's foot say how many were folded and dropped. A record's classification flags (caption, support record) are likewise taken by majority over its attested appearances, not from any one copy.
* **Impossible continuity indices are re-read.** A misread continuity index can claim up to fifteen lost packets and push every byte after it fifteen packets late. An index claiming more packets lost than there have been candidate lines since the group's last packet is read instead as the nearest possible index, and the report's data group section says how often that happened.
* Of the §5.2.8.4 link redefinitions, only a More Record address in the same data channel is followed; the channel-switching forms are left unresolved.
* Every run logs a recovery profile at debug level as part of the report: candidate lines carrying a burst, packets from each detector, and which gate discarded the rest.
